# RFP Insight

**제안요청서(RFP) PDF에서 핵심 정보를 추출하고 원문 근거를 검증하는 웹 애플리케이션**

RFP Insight는 공공기관·기업의 제안요청서를 읽고 사업명, 사업기간, 사업비, 사업목적, 제출기한을 구조화합니다. LLM이 생성한 값을 그대로 보여주는 데 그치지 않고, **원문 인용 검증과 복수 후보 선택**을 통해 결과를 검토할 수 있도록 만드는 개인 AI 엔지니어링 프로젝트입니다.

> **개발 상태:** 로컬 MVP 구현 및 평가 진행 중 · 2026년 10월 기준  
> **기술 스택:** Python 3.13, Streamlit, pypdf, Groq API (`openai/gpt-oss-20b`), unittest

## 1. 문제 정의

RFP는 수십 페이지에 걸쳐 사업 정보가 흩어져 있으며, 표지·사업 개요·입찰 서식에 동일한 정보가 서로 다르게 표기되기도 합니다. 단순한 LLM 추출만으로는 다음 문제가 남습니다.

- 공식 사업명과 축약 사업명이 별도 후보로 추출됨
- 같은 사업기간이 요일·기간 설명 차이로 중복됨
- 인용 페이지가 잘못 지정되거나, 인용문이 원문과 일치하지 않음
- 사업비의 금액·상한·VAT 조건이 누락될 수 있음

이 프로젝트는 **정보 추출 → 후보 병합 → 근거 기반 선택 → 검증 → 결과 표시**로 처리 단계를 분리하여 문제를 해결하고자 합니다.

## 2. 구현된 기능

| 기능 | 현재 구현 내용 |
| --- | --- |
| PDF 업로드·텍스트 추출 | `pypdf`로 페이지별 본문 및 페이지 번호 추출 |
| LLM 기반 구조화 | Groq API로 5개 항목을 JSON 형식으로 추출하고 인용문·페이지 번호 수집 |
| 그룹별 분석 | 문서를 3페이지씩 나누어 순차 분석하며 진행률 표시 |
| 로컬 캐시·복원 | PDF SHA-256 해시와 그룹 크기를 기준으로 결과 저장 및 재사용 |
| 후보 병합 | 동일한 문자열을 정규화하여 중복 후보 수집·통합 |
| 후보 선택 | 사업명은 사업 개요와 입찰 서식 교차 확인, 사업기간은 시작 기준·종료일 비교 |
| 사업비 검증 | 금액 및 일부 조건을 추출값·원문 근거와 비교하여 경고 표시 |
| 원문 인용 검증 | 인용문이 지정한 PDF 페이지에 존재하는지 확인하고, 다른 페이지에서 발견되면 위치 제시 |
| Streamlit 화면 | 최종 대표값 우선 표시, 원본 후보 및 근거 검증 상세 정보 별도 제공 |
| 평가·테스트 | 정답 JSON을 이용한 자동/수동 평가, 단위 테스트 및 회귀 테스트 |

대표값의 근거가 충분하지 않으면 무리하게 하나를 선택하지 않고 `검토 필요` 상태로 남깁니다.

## 3. 처리 흐름

```text
PDF 업로드
   ↓
pypdf 페이지별 텍스트 추출
   ↓
3페이지 단위 그룹 생성
   ↓
Groq LLM → 항목별 값 + 인용문 + 페이지 번호
   ↓
그룹 결과 캐시 저장 (SHA-256 기반)
   ↓
result_merger.py → 중복 후보 병합
   ↓
candidate_resolver.py → 근거 기반 대표값 선택
   ↓
원문 인용·사업비 검증
   ↓
Streamlit 최종 결과 및 상세 후보 표시
```

**분리한 이유:** LLM 추출 결과, 후보 병합, 최종 선택, 근거 검증을 각각 관찰하고 테스트할 수 있도록 하기 위해서입니다.

## 4. 검증 결과

### 45페이지 LMS RFP

| 지표 | 결과 | 해석 |
| --- | --- | --- |
| 기존 후보 병합 기준 자동 일치 | **2/4 (50%)** | 복수 후보를 확정하지 못한 항목 포함 |
| 후보 선택 알고리즘 적용 후 자동 일치 | **4/4 (100%)** | 동일 문서의 사업명·사업기간 대표값 선택 개선 |
| 후보 탐지 | **4/4** | 정답 후보 발견 또는 원문에 없는 항목의 올바른 미추출 |
| 사업목적 수동 의미 평가 | **1/1** | 사람이 핵심 의미 보존 여부 확인 |
| 원문 근거 일치 | **6/9 (66.7%)** | 인용문과 지정 페이지의 일치 여부 |

### K-sure RFP 회귀 검증

- 사업명·사업기간·사업비: **3/3 PASS**
- 기존 원문 근거 검증: **5/6 일치**
- `unittest` 기반 후보 선택 규칙 테스트: **4개 통과**

**해석 시 주의:** LMS 문서는 후보 선택 규칙 개발에도 활용한 문서입니다. 따라서 4/4는 **해당 개발 문서에서의 개선 결과**이며, 독립 평가 데이터나 일반적인 RFP 전체에 대한 정확도 100%를 의미하지 않습니다. 개선은 **LLM 자체가 아닌 후처리 후보 선택 알고리즘**에서 이루어졌습니다. 원문 인용 일치율과 사업목적 요약 품질은 별도 개선 과제입니다.

## 5. 주요 파일

```text
app.py                           # Streamlit 웹 애플리케이션
requirements.txt                 # Python 의존성
src/
  pdf_loader.py                  # PDF 텍스트 추출
  rfp_analyzer.py                # Groq LLM 호출·JSON 추출
  result_merger.py               # 그룹별 후보 병합
  candidate_resolver.py          # 사업명·사업기간 대표값 선택
  source_validator.py            # 원문 인용·페이지 검증
  value_validator.py             # 원문 근거와 사업비 금액 비교
  result_store.py                # 분석 결과 캐시 저장·복원
scripts/
  evaluate_rfp.py                # 베이스라인 전후 평가
  evaluate_k_sure.py             # 초기 K-sure 평가 스크립트
evaluation/
  k_sure_gold.json               # K-sure 기준 답안
  second_rfp_gold.json           # LMS 기준 답안
tests/
  test_candidate_resolver.py     # 후보 선택 단위 테스트
```

`data/`의 원본 PDF, 분석 캐시, 베이스라인과 평가 보고서는 저장소에 포함하지 않습니다.

## 6. 로컬 실행

Python 3.13 환경을 기준으로 개발했습니다.

```bash
# 저장소 복제
git clone https://github.com/itsyoojong/rfp-summary.git
cd rfp-summary

# 가상환경 생성·활성화 (macOS/Linux)
python3 -m venv .venv
source .venv/bin/activate

# 의존성 설치
python -m pip install -r requirements.txt
```

프로젝트 루트에 `.env` 파일을 만들고 본인의 Groq API 키를 설정합니다.

```dotenv
GROQ_API_KEY=your_groq_api_key
```

다음 명령으로 서비스를 실행합니다.

```bash
python -m streamlit run app.py
```

PDF를 업로드한 뒤 그룹별 분석 버튼을 사용해 분석을 진행합니다. 저장된 분석 결과가 있으면 동일한 문서를 다시 업로드했을 때 캐시에서 복원합니다.

## 7. 테스트 및 평가 실행

후보 선택 알고리즘 단위 테스트:

```bash
python -m unittest discover -s tests -p 'test_candidate_resolver.py' -v
```

저장된 베이스라인을 이용한 평가 예시:

```bash
python -m scripts.evaluate_rfp \
  --pdf data/second_rfp.pdf \
  --gold evaluation/second_rfp_gold.json \
  --baseline data/baselines/second_rfp_baseline_v1.json
```

평가 명령은 **해당 PDF와 베이스라인 JSON이 로컬에 준비된 경우에만** 실행됩니다. 두 파일은 GitHub 저장소에 포함되지 않으며, 평가 자체는 저장된 결과를 사용하므로 Groq API를 다시 호출하지 않습니다.

## 8. 현재 한계 및 다음 작업

- **원문 인용:** 잘못 지정된 페이지와 긴 인용문의 불일치 문제 해결 필요
- **사업목적:** 핵심 의미를 보존하면서 간결하게 요약하는 후처리 및 별도 품질 평가 필요
- **PDF 구조:** 다단 편집·표·서식에서 추출 텍스트가 섞일 수 있음
- **후보 선택:** 현재 규칙은 특정 사업명 레이블과 종료일 형식에 의존하며, 다양한 RFP에서 추가 검증이 필요
- **평가 범위:** 문서 수를 늘리고 개발에 사용하지 않은 문서에서 일반화 성능 검증 필요
- **서비스 운영:** 배포·운영 환경 정비는 향후 과제

## 9. 보안 및 데이터 관리

- API 키는 `.env`에 저장하고 Git에 커밋하지 않습니다.
- 원본 RFP, 캐시 및 평가 보고서는 `data/` 아래 로컬 파일로 관리합니다.
- 외부 문서 분석 시 문서의 공개 여부와 API 전송 가능 여부를 확인해야 합니다.
